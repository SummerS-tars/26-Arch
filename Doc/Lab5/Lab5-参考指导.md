# Lab 5 (异常与中断处理) 实施规划与知识图谱
为了确保对原项目要求的零遗漏，并能够体系化地推进开发与验证，现将 Lab 5 的支持与完善工作划分为 **5 个核心演进阶段**。

## 阶段一：CSR 寄存器堆与 Zicsr 特权指令集支持
**目标**：构建用于记录 CPU 系统状态的核心容器，使 CPU 具备理解特权级配置的能力。

- **背景知识梳理**：
  - **CSR (Control and Status Register)**：不同于通用寄存器，CSR 专用于存储 CPU 的运行状态和控制配置。
  - **核心寄存器**：重点理解 `mstatus`（全局中断使能）、`mtvec`（异常处理基址）、`mepc`（被中断的指令地址）、`mcause`（陷入原因）、`mscratch`（上下文切换的暂存器）。
  - **Zicsr 指令**：深入理解 `csrrw` (读写), `csrrs` (读置位), `csrrc` (读清零) 的原子级操作语义。
- **规划行动**：
  1. 在 `core_csr.sv` 中实例化上述核心 CSR。
  2. 修改 `core_decode.sv`，扩展对上述 Zicsr 指令以及 `ecall`、`mret` 的指令译码支持。
  3. 建立自 ID（译码段）到 CSR 模块读取数据，再将结果前推或写回至 WB（写回段）的数据通路。
- **验收条件**：
  - 通过基础单步指令测试，能够使用汇编正确写入并读出指定的 CSR 寄存器，所有位操作（置位、清零）结果符合 RISC-V 规范预期。

## 阶段二：Trap（陷入）控制器与异常路由
**目标**：构建精确异常 (Precise Exception) 捕获能力，实现从普通应用模式到 Machine Mode 内核层的上下文跳转。

- **背景知识梳理**：
  - **精确异常**：当异常发生时，异常指令之前的指令必须全部安全完成，而异常指令本身及其之后的指令不得对寄存器或内存留下任何状态篡改。
  - **陷入机制 (Trap)**：通过 `ecall` 发起系统调用，或执行非法指令时，CPU 需硬件自动拦截，保存现场并移交控制权。
- **规划行动**：
  1. 引入独立的 `Trap Controller` 逻辑，监控流水线 MEM 或 EX 阶段的异常标志位。
  2. 捕获到异常时，硬件自动：更新 `mcause`，将当前发生异常的 PC 存入 `mepc`，并拉低 `mstatus.MIE`（关闭全局中断防嵌套）。
  3. 劫持下一时钟周期的 PC，强制重定向至 `mtvec` 中存储的异常服务程序基址。
- **验收条件**：
  - 执行 `ecall` 后，PC 精准跳转至目标服务程序，且随后能通过 `mret` 指令完美恢复回原 `mepc` 地址继续执行。

## 阶段三：流水线冲刷 (Pipeline Flush) 与冒险控制升级
**目标**：解决中断或异常带来的最高优先级“控制冒险”，确保流水线数据的绝对安全。

- **背景知识梳理**：
  - **硬件级回滚**：异常随时可能发生且不是普通的分支跳转。处理这种硬件状态的强制回滚与冲刷时，其工程理念与优化自建高并发游戏服务器中的状态机同步颇为相似——必须保证主运行循环（流水线推进）不能卡死，且状态转换时绝不残留无效的“脏数据帧”。
- **规划行动**：
  1. 升级现有的 `core_hazard_unit.sv` 控制枢纽。
  2. 当 Trap 触发或执行 `mret` 时，立即发出全局异常 Flush 信号。
  3. 将 IF/ID 和 ID/EX 之间的流水线寄存器强制清零（注入气泡 `NOP`），废弃掉那些已经被预取但还没有实质性执行的“未来指令”。
- **验收条件**：
  - 在流水线满载状态下人为触发异常，被废弃的“后续指令”绝对不会向通用寄存器写回错误数据，也不会对 BRAM 产生任何破坏性写操作。

## 阶段四：CLINT 外设对接与 Timer 异步中断
**目标**：实现外设硬件定时器中断，赋予简易 OS 内核进行任务时间片轮转的能力。

- **背景知识梳理**：
  - **同步异常与异步中断**：`ecall` 是指令流内部同步产生的，而定时器属于外部设备，不受指令流控制，随时可能拉低 CPU 引脚发出异步中断。
  - **MMIO（内存映射 I/O）**：把外设寄存器当成普通内存地址来读写通信（如 `mtime` 与 `mtimecmp`）。
- **规划行动**：
  1. 编写简易 CLINT（核心本地中断器）模块，内部维护一个 64 位自增计时器 `mtime`。
  2. 充分复用 Lab 3 已跑通的 CBus 总线体系，为 CLINT 分配独立的 MMIO 物理寻址空间。
  3. 当 `mtime >= mtimecmp` 时，触发外部中断引脚 `irq`，CPU 核心在指令提交时检测到该信号，且 `mstatus.MIE` 为 1 时发起 Trap。
- **验收条件**：
  - CPU 能通过标准的 `sw/lw` 指令正确配置定时阈值；当计时器达标后，能够正确打断当前执行流进入中断处理函数（ISR）。

## 阶段五：OS Kernel 联调与自动化回归测试
**目标**：拉起微型操作系统验证环境，确保软硬件全链路协同无死锁、不跑飞。

- **背景知识梳理**：
  - **软硬协同验证 (Hardware/Software Co-simulation)**：OS 的稳定运行高度依赖底层 CPU 硬件特权指令的完备程度。
  - **差异化测试 (Differential Testing)**：通过对比被测硬件（RTL 模型）与黄金标准环境（如 NEMU 模拟器）在处理相同指令序列时的寄存器变化规律来找 Bug。
- **规划行动**：
  1. 利用脚本将仓库 `ready-to-run/lab5/` 目录下的 `kernel.bin`/`.coe` 固件装载进入 SoC 系统存储中。
  2. 借助在构建高吞吐率后端自动化评估系统中积累的日志比对与监控探针经验：利用 Verilator 结合 Python 编写一套自动化回归跑测框架。
  3. 让脚本自动抓取 Verilator 吐出的每步 PC Trace 和 CSR 状态变动，与标准参考模型的执行日志进行自动化 diff 比对。
- **验收条件**：
  - OS Kernel 成功在仿真环境中加载启动，支持持续的上下文时钟轮询；自动化回归测试框架能够覆盖各类异常与特权指令边界，并在所有测试集上全绿通过。
